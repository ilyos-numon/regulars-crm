만든 방법

문제

작은 가게 사장님은 단골을 얼굴로 기억하지만, 발길이 끊긴 걸 알아채는 건 늘 늦습니다. 일괄 ‘30일 미방문’ 규칙은 닷새마다 오던 분과 2주마다 오던 분을 같은 잣대로 재고, 손에 있는 자료는 카드 매출 CSV(거래일시·카드번호·금액·상품명) 하나뿐입니다. 이름·전화번호 없이 이 기록만으로 판단해야 했습니다.

판단 방식

  1. 손님마다 평소 간격. 카드번호를 해시와 끝 두 자리로 바꾼 뒤, 결제한 날이 사흘 이상이고 평균 간격이 15일 이하인 손님을 단골로 보고 그 사람의 평소 방문 간격을 따로 잽니다.
  2. 2배 기준. 마지막 방문 뒤 지난 날수를 평소 간격으로 나눈 지연 배수가 2.0 이상이면 이번 주 챙길 단골 후보가 됩니다.
  3. 비·연휴·메모 보정. 2026 관공서 공휴일과 강수량 10mm 이상인 날을 빼고 다시 재고, 사장님 메모가 있는 손님은 기준을 3배로 올려 미뤄 둡니다.
  4. 가게 쪽 원인 먼저. 14일 안에 여러 단골이 함께 끊겼으면 손님 탓보다 리뷰 별점·날씨 같은 가게 쪽 원인을 먼저 보여 줍니다.

Node·TypeScript 서버가 카드사 매출 CSV(거래일시·카드번호·금액·상품명)를 읽어 카드번호를 해시와 끝 두 자리로 바꾸고, 손님마다 평소 방문 간격과 지연 배수를 계산합니다. 2026 공휴일·비 온 날·사장님 메모를 보정 단계로 거친 결과를 기능 8개(브리핑·복귀 확인·메모·날씨·리뷰·원인 힌트·안부 문구·손님 기록)가 같이 씁니다. 저장은 JSON 파일, 화면은 빌드 없는 정적 HTML 과 GSAP, 월요일 09:00 브리핑은 주간 워크플로가 API 를 불러 메신저로 보냅니다. 안부 문구는 OpenAI 호환 LLM 키가 있으면 다듬고 없으면 기본 문구로 동작하며, 단위 테스트와 Playwright 화면 테스트로 검증합니다. 공개 저장소 github.com/ilyos-numon/regulars-crm
